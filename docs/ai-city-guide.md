# AI 城市嚮導（3D NPC）規劃

2026-11-07 · 規劃中 · 交給 LLM 負責的隊員開發

使用者在城市地圖裡問問題，手機上的模型用白話回答；城市裡的嚮導小人沿著馬路走到相關的大樓，打開那一類的步驟，一站一站帶著辦完。

> 例：「爸爸中風快出院了，我要申請什麼？」→ 嚮導回答三件事要辦，接著走到「傷病與醫療」大樓打開「出院返家照顧」，辦完再帶你去「高齡與長照」、「身心障礙」。

## 1. 先讀：比賽規則對這個功能的限制

出自入門指引第 06 章「AI 使用指引」與競賽須知（115.08.27 版）。

| 規則 | 對我們的影響 |
| --- | --- |
| 執行時的推論必須在手機端完成，不可呼叫雲端 API 或遠端模型 | 模型放在台北通 App 裡跑，網頁只負責送問題、收回答 |
| 評審可能**關閉網路**現場出題 | 模型、網頁、城市模型都要能離線使用，見[第 7 節](#7-斷網-demo)。Demo 前用飛航模式完整測一次 |
| 不可使用危害國家資通安全清單所列的 AI 工具與模型（含大陸廠牌） | Qwen、DeepSeek、GLM、Yi、MiniCPM、InternLM、Baichuan 這類模型都不能用（以官方清單為準）。**換大模型前先確認來源** |
| 套件要開源、免費 | 推論框架用入門指引列的 `flutter_edge_ai`（MIT）或 `llamadart`（MIT） |
| README 要揭露模型名稱、版本、量化格式、推論框架與來源 | 見[第 9 節](#9-繳交前要補的文件) |
| 決選有問答，評審會問設計考量 | AI 產生的程式碼要自己讀過一遍 |

模型建議：入門指引推薦 **Gemma 4 E2B**（2026/4 以 Apache 2.0 釋出，8 GB 記憶體手機較穩定）。之後想換大一點的，可以試 Gemma 4 E4B 或 Phi-4 Mini。小模型的繁體中文程度差很多，請用[第 4 節](#4-測試問題)的題目實測後再決定。

## 2. 選定情境：爸爸中風，下週出院

只準備一個情境。我們比較了目前五個有完整步驟的事件，再看哪一組能串起**最多棟大樓**。嚮導要「走到不同建築」，情境只落在一棟大樓的話就沒得走。

| 事件 | 大樓 | 步驟 | 資源 | 台北通服務 | 電話 | AR 地點 |
| --- | --- | --- | --- | --- | --- | --- |
| 申請身心障礙證明 | 身心障礙 | 5 | 9 | 5 | 1 | 3 |
| 家人疑似失智 | 高齡與長照 | 5 | 11 | 4 | 3 | 1 |
| 懷孕到生產 | 懷孕與育兒 | 6 | 9 | 6 | 0 | 1 |
| 出院返家照顧 | 傷病與醫療 | 5 | 9 | 5 | 2 | 0 |
| 申請長照服務 | 高齡與長照 | 4 | 9 | 3 | 2 | 0 |
| 親人過世 | 身後事 | 5 | 7 | 4 | 0 | 1 |

單一事件裡沒有誰特別突出，但「中風出院」可以把三個事件串成一條路線：

| 站 | 大樓（`categoryId`） | 事件（`eventId`） | 步驟 |
| --- | --- | --- | --- |
| 1 | 傷病與醫療（`health`） | 出院返家照顧（`discharge-home`） | 出院準備、借用輔具、回診交通、請假與給付、回到日常 |
| 2 | 高齡與長照（`elder-care`） | 申請長照服務（`long-term-care`） | 申請長照評估、到府評估、擬定照顧計畫、照顧者也要被照顧 |
| 3 | 身心障礙（`disability`） | 申請身心障礙證明（`disability-certificate`） | 到區公所申請、醫院鑑定、需求評估、領取證明、申請福利 |
| 終點 | 照顧者支持（`caregiver`） | （內容建置中） | 接第 2 站最後一步：喘息服務、支持團體 |

合計 14 步、27 項資源、13 個台北通服務、5 支電話、3 個 AR 地點，用到七種辦理方式裡的六種（臨櫃、到醫院、電話、在家、等候、線上）。這是目前功能最多的組合，也剛好是使用者舉的例子。故事也接得上計畫書：故事四（黃大哥中風後申請身障證明）加上故事一（照顧者第一次知道喘息服務）。

**情境人物**（虛構）：陳小姐 45 歲，72 歲的爸爸中風住院，下週出院，出院後左側無力、需要輪椅。她要「幫家人辦」。

**待查證**：中風後多久可以做身障鑑定、長照評估能不能在住院時先申請等時間點，回答前要先對照官方資料。目前的步驟內容是示範資料，嚮導回答時也要這樣說明。

## 3. 使用流程

1. 打開城市地圖，嚮導小人站在城市前方的人行道上，頭上有「問我」的小提示。
2. 點嚮導或「問問城市嚮導」按鈕，打開對話框。對話框裡有建議問題（[第 4 節](#4-測試問題)），點了就送出，不用打字。也可以自己輸入。
3. 送出後，嚮導頭上顯示「想一想⋯」。第一次使用時模型要載入，改顯示「準備中，第一次大約要等幾十秒」。
4. 回答一個字一個字出現在對話框。可以按「朗讀」，沿用 `src/services/speech.ts`。
5. 回答下方出現「帶我去」。按下後嚮導沿著馬路走到第 1 站，那棟大樓被選取（沿用現有的選取：浮起、拉近），底部抽屜打開那個事件。
6. 抽屜裡多一個「下一站：高齡與長照」。按了嚮導就走到下一棟，依序**解鎖**後面的站。
7. 走到終點，嚮導說「照顧家人辛苦了，自己也要休息」，並給「撥打 1999」與「撥打 1966」兩個按鈕。
8. 打勾的進度和清單、地圖共用 `stores/progress`。下次回來，嚮導會從還沒辦完的那一站接著帶。

問到情境以外的事（例如「我要結婚」），嚮導說明目前只示範中風出院的情境，並建議點「婚姻與家庭」大樓自己看，或撥 1999。

## 4. 測試問題

這些題目同時是對話框的建議問題，也是調整提示詞用的測試題。

**題目不用綁死這八題，依實際模型的能力調整。** 手機上的小模型理解力和 context 長度都有限，實測後答不好的題目就拿掉或改簡單，只把答得穩的放進建議問題。模型太弱或 context 不夠時，可以這樣縮：

- 題目減到只剩「整條路線」加兩三個單一步驟的問題
- 情境資料只留每一站的事件名稱與步驟標題，不放步驟說明
- 範例從兩個減成一個，或只留輸出格式說明
- 動作標籤只留 `[[ROUTE]]` 與 `[[NONE]]`，單一步驟交給網頁的關鍵字備援判斷
- 換更大的模型後再把題目加回來

| 問題 | 期望的動作 | 期望回答的重點 |
| --- | --- | --- |
| 爸爸中風快出院了，我要申請什麼？ | 整條路線 | 先安排出院與輔具，再申請長照，之後評估身障證明 |
| 出院後輪椅去哪裡借？ | 第 1 站・借用輔具 | 輔具資源中心可以租借，可能有輔具補助 |
| 回診要怎麼去醫院？ | 第 1 站・回診交通 | 無障礙計程車、復康巴士，不確定撥 1999 |
| 長照要怎麼申請？ | 第 2 站・申請長照評估 | 撥 1966，之後會有專員到府評估 |
| 爸爸需要申請身心障礙證明嗎？ | 第 3 站・到區公所申請 | 先到區公所領鑑定表，再到醫院鑑定；是否符合由鑑定決定 |
| 我照顧爸爸好累 | 第 2 站・照顧者也要被照顧 → 終點 | 喘息服務、家庭照顧者支持據點 |
| 我要結婚 | 不移動 | 目前只示範中風出院；可點婚姻與家庭大樓或撥 1999 |
| 爸爸這樣算重度嗎？ | 不移動 | 不能判斷，要由醫院鑑定；可撥 1957 福利諮詢專線 |

## 5. 架構

```
┌─────────────── 台北通 App（Flutter）────────────────┐
│                                                      │
│  WebView：微服務網頁                                  │
│  ┌────────────────────────────┐                      │
│  │ 城市地圖  ＋ 嚮導小人        │                      │
│  │ 對話框（問題、串流回答）     │                      │
│  └──────┬─────────────────────┘                      │
│         │ flutterObject.postMessage('llm_ask')        │
│         ▼                                             │
│  LlmMessageHandler（自訂 TPWebMessageHandler）        │
│         │                                             │
│         ▼                                             │
│  手機端推論：flutter_edge_ai 或 llamadart ＋ 模型檔    │
│         │ 一段一段回覆（delta）                        │
│         ▼                                             │
│  網頁收到回答 → 顯示文字 → 解析動作 → 嚮導走路、開抽屜 │
└──────────────────────────────────────────────────────┘
```

**最重要的設計：模型只負責「聽懂問題、用白話回答、選一個動作」，路線與步驟內容由程式決定。**

- 模型從固定的清單裡選動作（[5.2](#52-提示詞與輸出格式)），不自己編地點、電話、補助名稱。
- 走哪條路、抽屜打開哪一步，都由網頁依 `src/data/lifeEvents.ts` 決定，所以不會出現模型亂編的政府資訊。
- 2B 這種小模型寫長篇 JSON 很容易格式錯，只要它在最後輸出一個標籤，穩定得多。

### 5.1 網頁與 App 的訊息格式

沿用現有的 `flutterObject` 雙向溝通（`lib/util/web_message_handler/`），新增三個 `name`，不可和內建的重複。

**網頁 → App**

```jsonc
// 問問題。提示詞由網頁組好送過去，改提示詞只要重新部署網頁，不用重 build App
{
  "name": "llm_ask",
  "data": {
    "id": "q-1731000000000",          // 網頁產生，回覆時帶回來對應
    "system": "你是台北通的城市嚮導……", // 第 5.2 節的提示詞（含情境資料）
    "messages": [{ "role": "user", "content": "爸爸中風快出院了，我要申請什麼？" }],
    "maxTokens": 256,
    "temperature": 0.3
  }
}

// 查模型狀態：用來顯示「準備中」、決定要不要先預熱
{ "name": "llm_status", "data": null }

// 使用者關掉對話框或換問題時中斷
{ "name": "llm_cancel", "data": { "id": "q-1731000000000" } }
```

**App → 網頁**（`llm_ask` 會回覆很多次）

```jsonc
{ "name": "llm_ask", "data": { "id": "q-…", "type": "delta", "text": "先安排" } }
{ "name": "llm_ask", "data": { "id": "q-…", "type": "done", "text": "（完整回答）", "model": "gemma-4-e2b-it-int4" } }
{ "name": "llm_ask", "data": { "id": "q-…", "type": "error", "code": "not_ready", "message": "模型還在載入" } }
// code：not_ready（還在載入）、busy（上一題還沒答完）、failed（推論失敗）

{ "name": "llm_status", "data": { "ready": true, "loading": false, "model": "gemma-4-e2b-it-int4" } }
```

**App 端（LLM 隊員）**

- 照入門指引的寫法新增 `LlmMessageHandler extends TPWebMessageHandler`，`name` 為 `llm_ask`，加進 `tp_web_message_listener.dart` 的 `_cachedMessageHandlers`。`llm_status`、`llm_cancel` 各一個 handler。
- 串流：每產生一段文字就呼叫一次 `onReply`。`replyProxy.postMessage` 可以呼叫多次，但請先在實機上確認。
- 一次只處理一題：上一題還沒答完就收到新的，回 `busy`，或先取消舊的。
- App 啟動或第一次打開服務時先載入模型並預熱，跑一次很短的推論。入門指引提醒：首次載入要數十秒。
- 提示詞與回答可能含健康資訊，不要寫進 log。

**網頁端（前端）**

- `src/services/townpass.ts` 現在的請求寫法收到第一則回覆就移除監聽，串流要另寫一個依 `id` 持續接收、收到 `done` 或 `error` 才移除的版本。
- 不在 App 裡（電腦瀏覽器開發）時改用**模擬模型**：照第 4 節的題目回固定答案、一段一段送出，前端不用等手機就能開發。模擬回答要標「示範回答」，不能讓人以為是 AI。

### 5.2 提示詞與輸出格式

給小模型的原則：短、規則具體、附範例。提示詞加情境資料盡量控制在 1,000 token 內。手機上提示詞越長，開始回答前等得越久，實際秒數以實測為準；框架支援的話，同一段系統提示詞重複使用，不要每題重算。

**情境資料**由網頁從 `lifeEvents.ts` 產生，每一步一行，例如：

```
[第1站 傷病與醫療｜出院返家照顧]
discharge-planning 出院準備：出院前請醫院協助規劃回家後的照顧
assistive-devices 借用輔具：租借輪椅、助行器等
return-visit-transport 回診交通：安排回診時的交通方式
……
[第2站 高齡與長照｜申請長照服務]
apply-ltc 申請長照評估：撥打 1966 長照專線提出申請
……
```

**系統提示詞草稿**（請依實測調整）：

```
你是台北通「一步一步來」城市裡的嚮導。使用者是照顧家人的家屬，正在問家人中風出院後要辦的事。

規則：
1. 用繁體中文、口語，像在跟長輩說話。回答不超過 100 個字，最多列 3 點。
2. 只能根據下面的「步驟資料」回答。資料裡沒有的事，說「這個我不確定，可以撥 1999 請專人協助」。
3. 不做醫療判斷，不保證一定符合補助；要說「可能可以申請，實際由機關審核」。
4. 這些步驟是示範資料，提到細節時提醒「出發前先打電話確認」。
5. 回答最後一行，從下面選一個動作標籤，原樣輸出：
   [[ROUTE]]        要辦的事不只一件，帶使用者走完整條路線
   [[STEP:步驟代號]] 只問到其中一步，代號從步驟資料裡選
   [[NONE]]         問題和中風出院無關，或不需要移動

步驟資料：
{{SCENARIO_CONTEXT}}

範例一
使用者：爸爸中風快出院了，我要申請什麼？
嚮導：辛苦了。可以照這個順序來：1. 出院前請醫院幫忙安排回家的照顧和輔具。2. 打 1966 申請長照評估。3. 之後再看要不要申請身心障礙證明。我帶你一站一站走。
[[ROUTE]]

範例二
使用者：輪椅去哪裡借？
嚮導：可以到臺北市輔具資源中心租借輪椅或助行器，也可能可以申請輔具補助。出發前先打電話確認喔。
[[STEP:assistive-devices]]
```

**網頁解析規則**

- 用 `/\[\[(ROUTE|NONE|STEP:[a-z-]+)\]\]/` 找最後一個標籤。標籤不顯示給使用者看。
- 標籤裡的步驟代號不在資料裡，就當作 `NONE`。
- **找不到標籤時的備援**：網頁用關鍵字自己判斷動作。例如「中風、出院」→ `ROUTE`，「輪椅、輔具」→ `assistive-devices`，「長照、1966」→ `apply-ltc`，「身障、證明」→ `apply`，「好累、喘息」→ `caregiver-care`。文字還是用模型的回答，這樣模型格式偶爾跑掉，Demo 也不會卡住。
- 模型完全不能用（載入失敗、手機不支援）時，對話框直接寫「AI 目前無法使用」，改列建議問題對應的固定說明並標「預設說明」。不可以假裝是 AI 回答。

### 5.3 嚮導小人

| 項目 | 規劃 |
| --- | --- |
| 模型 | Kenney [Mini Characters](https://kenney.nl/assets/mini-characters)（CC0，40 個模型）。和城市模型同一系列，風格一致 |
| 動畫 | 已確認內建 `idle`、`walk`、`emote-yes`、`interact-right`、`sit`，另有整套輪椅動畫（`wheelchair-sit`、`wheelchair-move-forward` 等） |
| 加分 | 套件附 `wheelchair-deluxe`、`aid-crutch`、`aid-cane` 等輔具模型，終點可以放一個坐輪椅的「爸爸」 |
| 大小 | 角色高約 0.7，大樓高 1.3–5；縮放約 0.35 倍 |
| 貼圖 | 和其他 Kenney 套件一樣指向 `Textures/colormap.png`，要放在自己的資料夾，例如 `public/city/characters/` |

**走路路線**：用道路中心線組成格狀路網，節點是路口，x、z 都是 −3.22、−1.05、1.05、3.22 的組合（`src/city/config.ts` 的 `PLOT_PITCH` 與外環道路）。每棟大樓在面向鏡頭那側的路上取一個「門口」點，用 BFS 找最短路徑後沿著折線走，轉彎時面向前進方向。速度約每秒 1.2 單位，鏡頭跟著小人移動。

**要在 `CityScene`（`src/city/scene.ts`）新增的介面**（前端實作）：

```ts
addGuide(): Promise<void>            // 載入角色，放在起點，播 idle
walkTo(categoryId: string): Promise<void> // 沿路走到大樓門口，走完 resolve
guideScreenPosition(): Vector2 | null     // 對話泡泡的位置，比照 screenPosition()
setGuideMood(mood: 'idle' | 'thinking' | 'talking' | 'happy'): void
```

- 現在的場景只在畫面變化時才重畫。角色走路或播動畫時要持續請求畫面，停下來就停，不然會一直耗電。
- 頭上的對話泡泡用 DOM 疊在畫面上，跟大樓標籤一樣，讀屏讀得到。
- 開啟「減少動態效果」時不播走路動畫，直接出現在目的地。

### 5.4 對話框

- **入口**：城市地圖的視角按鈕列旁加「問問城市嚮導」，點嚮導小人也會打開。
- **版面**：沿用 `BottomSheet`，地圖上方仍看得到嚮導。和類別抽屜共用同一個位置：嚮導帶路時，抽屜顯示事件步驟，上方加一列「嚮導：……　下一站 ›」。
- **內容**：對話紀錄、建議問題、文字輸入框（字級至少 16px，iPhone 才不會自動放大畫面）、送出、朗讀、模型狀態（準備中／可離線使用）。
- **固定提醒**：「AI 回答僅供參考，內容是示範資料，請以機關公告為準；需要真人協助請撥 1999。」
- **無障礙**：新回答出現時用 `aria-live="polite"` 讀出；所有按鈕 48px 以上；不用語音也能完整操作。

## 7. 斷網 Demo

模型在手機上，斷網也能推論；**但網頁目前是從 Cloudflare Pages 線上載入的**，斷網時打不開。城市地圖的 Three.js 與模型檔（約 2 MB）也是要用時才下載。可選的做法：

| 做法 | 優點 | 缺點 |
| --- | --- | --- |
| A. 網頁加 Service Worker，先把頁面、程式與模型檔存起來 | 網頁照常部署，App 不用改 | iPhone 的 WebView（WKWebView）要另外設定 App-Bound Domains 才支援 Service Worker，要先實測 |
| B. 把 `dist/` 打包進 App，用 flutter_inappwebview 從本機載入 | 一定能離線 | 每次改網頁都要重 build App；Android 不允許 http，要用 https 的本機載入方式 |
| C. 只靠「先連網打開過一次」 | 不用改程式 | 要確認快取設定讓程式檔與模型檔留在手機上；App 被關掉就沒了，風險最高 |

建議先用 C 讓 Demo 能跑，再評估 A 在 Android、iPhone 上能不能用。**最晚在比賽第二天上台前，用飛航模式從開 App 到嚮導走完一站完整測一次。**
